# 青韵智控第一批做青采样 SOP

> 目的：保证第一批真实做青数据可追溯、可复盘、可用于后续建模，而不是只留下几条曲线和几张照片。
>
> 第一批真实实验定位为：**被动监测 + 人工事件标记 + 师傅判断记录**。第一批不建议直接让系统自动控制做青工艺。

---

# 1. 批次编号

统一格式：

```text
BATCH_YYYYMMDD_XXX
```

示例：

```text
BATCH_20260916_001
```

每个批次独立文件夹，禁止多个批次混存。

---

# 2. 实验前必须记录的元数据

## 2.1 鲜叶信息

- 品种；
- 采摘日期；
- 采摘时间段；
- 采摘地点；
- 采摘标准；
- 原料总质量；
- 初始含水相关信息（如有）；
- 鲜叶外观描述；
- 是否经历运输 / 冷藏；
- 从采摘到实验开始的时间。

## 2.2 环境信息

- 日期；
- 天气；
- 室内 / 室外；
- 初始温度；
- 初始相对湿度；
- 做青场地；
- 空调 / 除湿 / 风机等环境设备状态。

## 2.3 设备信息

- MVP 版本；
- MCU 固件版本；
- 上位机版本；
- MOS 传感器编号；
- 温湿度传感器编号；
- 称重模块编号；
- 相机编号；
- 气泵 / 阀状态；
- 采样气路版本。

不要只记“ESP32”“电子鼻”，应能追溯到本次实验具体设备。

---

# 3. 实验前设备准备

## 3.1 MOS 阵列

- 新传感器首次使用的预热 / 老化时间遵循器件手册；
- 每次实验开始前至少完成稳定预热；
- 记录预热开始时间；
- 记录清洁空气下各通道初始基线；
- 若某一路明显偏离历史范围，先排查，不直接进入正式采样。

## 3.2 气路

检查：

- 管路无明显折弯；
- 接头无松动；
- 气泵运行正常；
- 采样阀正常；
- 清洗阀正常；
- 气室无明显残留气味；
- 过滤件安装正确。

在正式鲜叶进入前完成至少 1 次完整：

> purge → baseline → sample test → purge

确认自动时序正常。

## 3.3 称重

- 空载归零；
- 用标准质量进行至少 2 点校验；
- 记录标定值；
- 确认机械结构无卡住 / 侧向受力。

## 3.4 RGB

固定：

- 相机位置；
- 镜头方向；
- 距离；
- 补光；
- 曝光；
- 白平衡；
- 背景。

若当天调整任何参数，必须记录。

---

# 4. 初始状态采集

定义 `T0`：

> **鲜叶进入本项目监测流程后的统一起始时刻。**

在 T0 完成：

1. 原始鲜叶照片；
2. 初始质量 `m0`；
3. 初始 MOS 基线与样气响应；
4. 初始叶温；
5. 环境温湿度；
6. 师傅 / 操作者初始描述；
7. 开始录像或关键节点视频记录。

`m0` 必须统一在 T0 定义，后续失水率计算全部以同一标准执行。

---

# 5. 采样频率建议

以下为第一批的初始方案，可在预实验后调整。

## 连续传感量

- MOS：1 Hz 原始采样；
- 环境温湿度：1 Hz；
- 叶温：0.2–1 Hz；
- 称重：1–10 Hz 原始采样，后处理取稳定窗口平均。

## RGB

建议：

- 常规静置：每 2–5 min 1 张；
- 摇青前：必拍；
- 摇青后：必拍；
- 师傅做关键判断时：必拍。

## MOS 气路采样

优先按自动周期运行：

```text
清洗 → 基线 → 采样 → 恢复
```

第一批宁可周期稍长，也不要为了时间分辨率牺牲恢复完整性。

---

# 6. 必须统一的事件标记

所有人工操作与工艺事件必须写入 `events.csv`。

推荐事件类型：

```text
BATCH_START
WITHER_START
SHAKE_START
SHAKE_END
REST_START
REST_END
MASTER_CHECK
MANUAL_SAMPLE
ENV_CHANGE
DEVICE_ERROR
DEVICE_RECOVER
FIXATION_START
BATCH_END
```

## SHAKE_START / SHAKE_END

必须同时记录：

- 时间；
- 转速 / 档位；
- 持续时间；
- 操作者；
- 本次为什么摇青；
- 是否属于原计划。

## MASTER_CHECK

师傅每次判断时记录：

- 时间；
- 当前判断；
- 判断依据；
- 建议下一步；
- 置信程度。

不要只写“可以了”“差不多”。

---

# 7. 师傅判断标签表

第一批重点不是构建完美标签体系，而是把主观经验结构化。

建议每次 `MASTER_CHECK` 至少记录：

| 维度 | 记录方式 |
|---|---|
| 青气 / 生青味 | 0–5 |
| 花香发展 | 0–5 |
| 果香发展 | 0–5 |
| 叶缘红变 | 0–5 |
| 柔软程度 | 0–5 |
| 失水感觉 | 偏低 / 合适 / 偏高 |
| 当前阶段 | 自由描述 + 后续统一编码 |
| 是否建议摇青 | 是 / 否 |
| 是否建议结束做青 | 是 / 否 |
| 备注 | 原话记录 |

评分标准在第一批结束后再根据实际描述修订。

严禁为了“标签整齐”在实验后擅自修改师傅原始判断。

可以另建一列做后处理统一编码。

---

# 8. 摇青前后固定采集窗口

每次摇青建议形成一个固定对照窗口。

## 摇青前

- 前 5–10 min 作为 pre-window；
- 记录稳定 MOS；
- 质量；
- 叶温；
- RGB；
- 师傅判断。

## 摇青中

- 记录开始 / 结束；
- 转速；
- 持续时间；
- 不把强振动时瞬时称重当作有效质量。

## 摇青后

建议固定记录：

- 立即；
- +5 min；
- +10 min；
- +20 min；
- 后续按常规周期。

这样便于分析机械刺激后 VOC、温度、视觉和失水变化。

---

# 9. 破坏性 Ground Truth 取样

如果有茶学 / 食品检测条件，可在少量关键节点取样。

候选节点：

- T0；
- 第一次摇青后；
- 中期关键节点；
- 最后一次摇青后；
- 做青结束。

可用于：

- 标准含水率；
- 茶多酚；
- 游离氨基酸；
- 香气组分；
- GC-MS。

注意：

- 每次破坏性取样都会改变剩余鲜叶质量；
- 必须记录取样质量；
- 失水率计算时需要决定是否做取样修正；
- 第一批如果检测资源不足，可以先不强行上 GC-MS。

第一批最重要的是把过程数据采完整。

# 10. 数据文件结构

每个批次建议：

```text
BATCH_YYYYMMDD_XXX/
├─ metadata.json
├─ sensors_raw.csv
├─ events.csv
├─ master_labels.csv
├─ images/
│  ├─ raw/
│  └─ keyframes/
├─ video/
├─ samples/
├─ notes.md
└─ checksum.txt
```

## metadata.json

放：

- 原料；
- 环境；
- 设备；
- 软件版本；
- 人员；
- 时间；
- 标定信息。

## sensors_raw.csv

只保存原始测量数据，不手工改值。

## events.csv

只保存事件。

## master_labels.csv

只保存人工判断。

这样后面可以独立调整标签编码而不破坏原始数据。

---

# 11. 异常处理规则

## 传感器掉线

立即记录：

```text
DEVICE_ERROR
```

包括：

- 哪个传感器；
- 开始时间；
- 原因；
- 恢复时间。

恢复后记录：

```text
DEVICE_RECOVER
```

不要删除中间异常时间段。

## MOS 饱和

若某通道长时间顶满：

- 记录；
- 增加清洗；
- 检查流量；
- 检查量程；
- 本批次继续保留原始数据。

不要在实验过程中为了“曲线好看”手动重置数据。

## 称重异常

强振动期间标记为无效称重窗口，不删除原始值。

## 相机失败

记录丢失帧区间，并保留其他模态，不因一个模态失败废弃整批数据。

---

# 12. 实验结束后 30 分钟内必须做的事

1. 确认所有数据文件已保存；
2. 复制原始数据到第二存储位置；
3. 检查文件大小是否合理；
4. 快速画出 MOS / 温湿度 / 叶温 / 重量时间序列；
5. 检查事件标记是否能对齐；
6. 把关键照片按时间点命名；
7. 写 `notes.md`；
8. 记录本次最明显的问题；
9. 更新 `docs/08_参赛证据台账.md`；
10. 不修改原始数据。

---

# 13. notes.md 最低内容

每批实验必须回答：

## 本批发生了什么

简述完整工艺过程。

## 哪些数据可信

例如：

- MOS 1–4 正常；
- MOS 5 恢复过慢；
- 叶温中段掉线 8 min；
- 称重在摇青期间振动严重。

## 最大异常

只写事实。

## 师傅最关键的 3 次判断

记录原话和时间点。

## 下一批只改哪几件事

建议不超过 3 项，避免一次改太多导致无法判断改动效果。

---

# 14. 第一批实验完成后的必做图

第一批不要急着训练复杂模型。

先画：

1. MOS 各通道 vs 时间；
2. 温度 / 湿度 vs 时间；
3. 叶温 vs 时间；
4. 质量 / 失水率 vs 时间；
5. 摇青事件叠加在时间轴；
6. 师傅判断叠加在时间轴；
7. 关键时间点鲜叶照片序列。

然后回答：

> 师傅认为状态发生变化的时刻，传感数据是否也出现一致或可解释的变化？

只有这个问题有初步肯定答案后，再讨论状态模型。

---

# 15. 第一批数据绝对不要做的事

- 不把同一批不同时间点随机拆成训练集和验证集并宣称泛化能力；
- 不只选“最好看”的通道；
- 不删掉失败曲线；
- 不为了准确率手工改标签；
- 不用一批数据得出“跨批次稳定”的结论；
- 不把相关性写成因果性；
- 不把示意性算法结果直接放入正式参赛成果页。

---

# 16. 第一批之后的数据计划

建议按批次推进：

## 1–3 批

目的：

- 跑通采集；
- 修设备；
- 修标签；
- 建 SOP。

## 4–10 批

目的：

- 初步分析多模态规律；
- 建第一版状态模型；
- 做单模态 / 多模态对比。

## 更多批次

逐步覆盖：

- 不同天气；
- 不同采摘时间；
- 不同初始失水；
- 不同茶季；
- 不同师傅 / 工艺。

真正的跨批次验证必须使用**完全未参与训练的整批数据**。

---

# 17. 与比赛证据的直接对应

第一批真实做青实验至少应产出：

- 1 组完整多模态时间序列；
- 1 套标准数据文件；
- 1 组完整工艺事件；
- 1 组师傅判断标签；
- 样机现场图；
- 真实实验图；
- 关键鲜叶状态图；
- 一份失败 / 问题记录；
- 下一版迭代计划。

这些材料比“先做一张很漂亮的算法准确率图”更重要。
