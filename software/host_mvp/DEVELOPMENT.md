更新日期：2026-09-22。适用范围：本目录当前工作区的 Host MVP v0.1 实现，包括新增的批次完整性检查；不代表已经发布或完成硬件验收。

## 1. 项目定位与文档入口

本程序是凤凰单丛做青实验的 Python 桌面采集上位机，负责串口接收、实时显示、批次存储、人工事件记录和手动拍照。当前阶段为被动监测，不执行泵阀控制或自动做青决策。

- [使用说明](README.md)：安装、启动和操作步骤。
- [第一阶段上位机与数据格式设计](../../docs/12_第一阶段上位机与数据格式设计.md)：目标架构与规划，其中部分功能尚未实现。
- 本文：当前代码结构、实际数据契约、开发入口、测试和已知限制。描述与代码不一致时，应核对实现并同步修改本文。

## 2. 目录与模块职责

```text
software/host_mvp/
├─ app.py                   程序入口、采集线程、批次记录和界面
├─ session_check.py         独立批次检查模块及命令行入口
├─ test_app.py              桌面模拟流程测试
├─ test_session_check.py    数据检查测试
├─ requirements.txt         运行依赖范围
├─ README.md                操作说明
└─ DEVELOPMENT.md           本开发文档
hardware/esp32_s3_mock/
└─ esp32_s3_mock.ino         Arduino 模拟串口发送端
data/raw/<batch_id>/         本地采集数据，默认不纳入 Git
```

| 代码入口 | 职责与主要接口 |
|---|---|
| `SensorReader(QThread)` | 串口或软件模拟数据源；`run()` 读取，`stop()` 请求停止；通过 `sensor(dict)`、`status(str)`、`error(str)` 发出信号 |
| `SessionLogger` | `start(batch_id, operator, mode)` 创建批次；`write_sensor(row)` 写传感器记录；`event(...)` 写事件；`image_path()` 生成照片路径；`stop()` 关闭文件并返回报告路径 |
| `MainWindow` | 连接和批次状态、事件按钮、曲线、质量/失水率显示、拍照、超时提示 |
| `audit_session(root)` | 读取批次目录并返回报告文本，不写文件 |
| `write_session_check(root)` | 调用检查并写入或覆盖 `session_check.txt`，返回路径，不修改原始 CSV |
| `parse_args()` / `main()` | 解析参数、创建 Qt 应用与窗口并进入事件循环 |

## 3. 开发环境与启动

当前面向 Windows，摄像头使用 DirectShow。README 推荐 Python 3.12；上一轮开发在 Windows / Python 3.14.4 上通过了 9 项自动测试，不能据此推断所有 Python 版本均已验证。

在 PowerShell 中执行：

```powershell
Set-Location D:\tiaozhan\software\host_mvp
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py --simulate
```

已有 `.venv` 时可跳过创建环境和安装步骤。直接使用环境内解释器，无需修改 PowerShell 执行策略。启动后点击“连接”，再点击“开始批次”。

| 参数 | 默认值 | 用途 |
|---|---|---|
| `--simulate` | 关闭 | 使用软件模拟数据，仍需在界面点击连接 |
| `--port` | `COM5` | 串口名称，可在界面修改 |
| `--baud` | `115200` | 串口波特率 |

串口示例：

```powershell
.\.venv\Scripts\python.exe app.py --port COM7 --baud 115200
```

依赖包括 PySide6-Essentials、pyqtgraph、pyserial、OpenCV 和 PyYAML，版本范围以 `requirements.txt` 为准。当前没有依赖锁文件；重建环境可能安装不同的兼容范围内版本。

## 4. 数据流与线程边界

```text
串口 JSON Lines / 软件模拟
          ↓ SensorReader（后台 QThread）
     Qt sensor 信号
          ↓ MainWindow.on_sensor（界面线程）
    基础格式判断 → seq 检查 → 字段映射
          ├─ SessionLogger → CSV + flush
          └─ 最近 600 个点 → 曲线及状态文字

界面事件 → SessionLogger.event → events.csv
手动拍照 → OpenCV → images/*.jpg + SNAPSHOT 事件
结束批次 → SESSION_END → 关闭 CSV → session_check.txt
```

目前只有数据源读取在后台线程；CSV 写入、绘图、相机读取和完整性检查都在界面线程。现有代码尚未达到设计文档中“采集、显示、存储完全分离”的目标。慢磁盘、相机阻塞或大批次检查可能造成界面停顿和信号积压。

主机时间在 `on_sensor()` 被界面线程处理时记录，不是串口线程收到字节的瞬间。因此主机时间间隔也可能反映界面调度延迟。曲线缓存为 600 个点，并非固定 600 秒；只有约 1 Hz 输入时才约等于 10 分钟。开始新批次不会清空曲线缓存或重置绘图时间原点。

## 5. 串口协议与字段映射

串口按 UTF-8 解码，每行一个 JSON 对象，以换行结束；读取超时为 1 秒。`type="sensor"` 进入采集流程，`type="status"` 显示 `message`，其他类型忽略。JSON 解析失败或根对象不是字典时显示错误并继续读取。

有效数据帧示例（发送时应为单行）：

```json
{"type":"sensor","seq":0,"t_ms":1000,"gas_adc":[15100,18800,13900,22000],"gas_v":[1.8876,2.3501,1.7376,2.7501],"bme688_gas_ohm":183000,"chamber_t_c":27.2,"chamber_rh_pct":71.0,"ambient_t_c":26.8,"ambient_rh_pct":69.0,"leaf_t_c":26.5,"mass_g":4000.0,"pump":1,"valve_sample":1,"valve_purge":0}
```

| 输入/来源 | `sensor_1hz.csv` 字段 | 含义 |
|---|---|---|
| 当前批次 | `batch_id` | 与批次目录名一致 |
| `seq` | `seq` | 非负整数序号，布尔值不接受 |
| 主机本地时区时间 | `datetime_iso` | 带时区 ISO 时间，毫秒精度 |
| 主机单调时钟 | `host_monotonic_s` | 秒，写入保留六位小数 |
| `t_ms` | `mcu_t_ms` | 设备毫秒计数；软件模拟模式使用主机单调时钟毫秒值 |
| `gas_adc` / `gas_v` | `gas_1_adc`…`gas_4_adc` / `gas_1_v`…`gas_4_v` | 四路 ADC 和电压，单位分别为计数与 V |
| `bme688_gas_ohm` | 同名 | 气体电阻，Ω |
| `chamber_t_c` / `ambient_t_c` / `leaf_t_c` | `chamber_temp_c` / `ambient_temp_c` / `leaf_temp_c` | 温度，℃ |
| `chamber_rh_pct` / `ambient_rh_pct` | 同名 | 相对湿度，% |
| `mass_g` | 同名 | 质量，g |
| `pump` / `valve_sample` / `valve_purge` | `pump_state` / `sample_valve_state` / `purge_valve_state` | 0/1 状态，仅记录 |
| 固件与上位机判断 | `quality_flag` | 保留固件标记，跳号时追加 `SERIAL_GAP`；旧数据源默认 `OK` |
| 固件/兼容默认值 | `gas_enabled_mask` | bit0..3表示启用的模拟通道；未提供时按15 |
| 已解析设备帧 | `device_frame_json` | 完整JSON，保留设备版本、诊断与标定参数；不是原始字节 |

在线检查要求 `seq` 合法且两个气敏字段为列表，否则整帧不写入 CSV。列表不足四项补空值，超过四项截断；其他字段缺失通常写为空值，由批次检查发现。当前不会保存原始串口字节或被拒绝的帧。

文件名中的 `1hz` 是协议约定，程序没有重采样或限频：输入几帧就处理几帧。固件应约每秒发送一帧。更改采样率时须同步修改文件约定、阈值、文档和测试。

## 6. 批次生命周期与存储

数据根目录通过 `app.py` 的位置计算，为仓库下的 `data/raw`，不随启动时的工作目录变化，目前没有命令行配置项。

1. 连接后锁定串口与模拟选项。开始批次时检查采集线程是否在运行；这不等价于已经收到有效设备数据，实际操作应先确认曲线更新。
2. 批次号为空时生成 `BATCH_yyyyMMdd_HHmmss`；允许 1–80 个 Unicode 字母/数字、下划线、短横线，拒绝路径分隔符及 Windows 保留名称。已有目录直接报错，不覆盖、不续写。
3. 创建 `images/`、`meta.yaml` 和两个 CSV，写入 `SESSION_START`。事件编号每批从 1 开始；空操作员写为 `unknown`。
4. 活动批次期间锁定连接按钮、批次号和操作员。数据来源取实际 reader 的 `simulate` 属性，写入 `experiment.source_mode`。
5. 首个有限、正数且非布尔的质量作为 `m0`，写 `T0_INITIAL`。界面失水率为 `(m0 - mt) / m0 × 100%`，不写入传感器 CSV，也不自动回填 `meta.yaml` 的初始质量字段。
6. 结束批次写 `SESSION_END`，关闭 CSV，然后同步生成检查报告。停止批次不会停止数据源，后续数据仅供界面显示。关闭窗口还会请求停止线程并释放相机。

```text
data/raw/<batch_id>/
├─ meta.yaml
├─ sensor_1hz.csv
├─ events.csv
├─ session_check.txt
└─ images/IMG_yyyyMMdd_HHmmss_fff.jpg
```

CSV 编码为 UTF-8 BOM，每次写记录后调用 `flush()`；YAML 和报告为 UTF-8。`flush()` 不等价于操作系统级持久化保证，断电或进程强退可能留下未完成批次。初始化失败时也可能保留部分目录，程序不会自动删除或覆盖。

`meta.yaml` 含批次、操作员、创建时间、设备版本字符串、协议与来源模式、原料字段。当前原料字段是空占位，硬件/固件版本为固定字符串，没有自动采集 Git SHA。串口来源 `serial` 只说明传输方式：ESP32 mock 固件的数据也是模拟数据，不能当作真实实验数据。

### 人工事件与图片

事件列为 `event_id,batch_id,host_time_iso,host_monotonic_s,event_type,event_value,operator,note`。

| 事件 | 当前触发方式 |
|---|---|
| `SESSION_START` / `SESSION_END` | 开始/结束批次自动记录 |
| `T0_INITIAL` | 首次有效初始质量自动记录，值形如 `mass_g=4000.000` |
| `SHAKE_START` / `SHAKE_END` | 摇青按钮，不强制成对或先后顺序 |
| `MASTER_CHECK` / `SAMPLE_TAKEN` | 师傅检查/取样按钮，支持自由备注 |
| `SNAPSHOT` | 拍照按钮，值为 `manual`；普通读取/保存失败时备注带 `camera failed` |

相机固定为索引 0，首次拍照时打开，请求分辨率 1920×1080，实际分辨率取决于设备。没有自动采图、图片预览、结构化师傅标签或图片索引；照片与事件未建立显式文件名关联。模拟传感器模式也不会模拟相机。

## 7. 完整性检查规则

结束批次正常完成时自动生成报告；强退或结束写入异常时不保证有报告。可单独重跑：

```powershell
Set-Location D:\tiaozhan\software\host_mvp
.\.venv\Scripts\python.exe session_check.py D:\tiaozhan\data\raw\BATCH_20260921_001
```

示例目录需换成实际批次目录。检查模块仅依赖 Python 标准库，可不安装桌面依赖直接运行。已有报告会被覆盖；原始数据保留。

| 检查项 | 当前规则 |
|---|---|
| 元数据 | `meta.yaml` 存在且非空；尚不解析 YAML 内容 |
| 传感器文件 | 能读取、有数据，要求的列存在 |
| 数值 | 必需数值字段可转为有限浮点数；空值、NaN、Inf 均报异常；mask禁用的气敏通道跳过数值检查；旧文件默认四路启用 |
| 序号 | 非负整数，相邻有效记录相差 1；重复、倒退、跳号均计为异常 |
| 时间 | 设备计数为非负整数；设备/主机单调时间严格递增；相邻差值超过 3000 ms / 3 s 报异常 |
| 范围 | 湿度 0–100%；质量与气体电阻非负；泵阀状态只能为 0 或 1 |
| 身份与日期 | 传感器和事件批次号须等于目录名；传感器日期可由 `datetime.fromisoformat` 解析 |
| 质量标记 | 统计全部标记；任何非 `OK` 或空标记计为异常 |
| 起止事件 | 恰好一个 START、一个 END，且分别为事件文件首尾记录 |
| 图片 | 统计 `images/` 下的 `*.jpg` 文件数量；零张不会单独报错 |
| 磁盘 | 检查时可用空间低于 1024 MiB 报异常，不代表全程空间情况 |

报告计数表示异常发生次数，不是缺失帧总数。无效数值会中断对应字段的相邻比较；尾段缺包、首帧之前的缺包和事件时间与采集时间的对齐尚未检查。设备计数回绕按倒退处理。日期仅检查可解析性，没有强制时区或检查系统时钟跳变。

目前未检查温度/ADC/电压的器件专用量程、图片内容、事件序号及摇青配对。CLI 正常写出报告即正常退出，即使报告内容为“发现异常”；自动化调用应读取报告，不可仅用退出码判断数据合格。基础检查通过不代表实验或传感器性能验证通过。

## 9. 故障定位与已知限制

| 现象 | 定位方式与处理 |
|---|---|
| 无法导入 PySide6 等模块 | 确认使用 `.venv` 内解释器，并按 requirements 安装 |
| 开始批次失败 | 查看弹窗；确认线程在运行、批次名合法且未重复、目录可写 |
| JSON parse error | 核对波特率、UTF-8、换行及 JSON 格式；当前没有跨超时片段重组或原始串口日志 |
| 数据超时 | 超过 3 秒没有被界面处理的基本有效帧会显示超时；检查设备与界面阻塞。设备已断开时看 DISCONNECTED/ERROR |
| SERIAL_GAP | 核对序号、设备重启与缺包；保留原始 CSV，由报告进一步检查 |
| 拍照失败 | 检查默认相机、权限、占用和 DirectShow 支持；当前没有相机选择或重开流程 |
| 写入失败/无报告 | 查看界面 ERROR；停止批次、保留现有文件，在恢复空间/权限后单独运行检查，不补造 SESSION_END |

日志当前仅显示在界面中，最多保留 300 个文本块，没有持久化设备健康日志。传感器 CSV 写入的 `OSError` 会触发结束批次；部分事件写入或 OpenCV 异常仍可能直接从回调抛出，统一异常处理尚未完成。关闭线程的等待有超时，但未实现超时后的完整收尾状态机。

上位机其他未实现功能：串口自动重连、自动快照、`image_index.csv`、`master_labels.csv`、SQLite 索引、泵阀/标定命令按钮及自动控制算法。真实传感器驱动与限时泵阀命令已在配套ESP32固件实现，尚未完成实物验收。

## 10. 软件开发路线与验收标准

更新日期：2026-09-22。以下为待开发计划；本次只更新文档，不表示功能已实现，也不改变第8节已有测试的覆盖范围。目标是将采集、设备操作、人工标签和数据回看串联起来，为第一批真实做青实验建立完整记录。

### 10.1 功能优先级

P0为下一轮重点，P1用于补齐数据管理，P2用于已有数据的回看与分析。优先级表示实施建议，不承诺交付日期。

| 编号 | 优先级 | 功能与范围 | 主要开发入口 | 验收标准（待执行） |
|---|---|---|---|---|
| SW-01 | P0 | 设备操作面板：设备信息、称重去皮、砝码标定、限时采样/清洗、停止 | `MainWindow` 与 `SensorReader`；复用固件 `info/tare/calibrate/air/stop` 命令 | 共用同一串口连接；发送、响应、超时均可追踪；拒绝响应不得显示成功；标定期间不能发起气路动作；断线后不自动重放动作命令 |
| SW-02 | P0 | 自动拍照与图片索引：默认每30秒采图，关键事件立即拍照，最新图片预览 | 将 `capture_snapshot` 拆为相机工作线程；扩展 `SessionLogger` | 成功图片均有 `image_index.csv` 记录，包含相对文件名、批次、时间与关联事件；失败有日志，不写虚假成功索引；采图不阻塞串口接收；停止批次后不串写到下一批 |
| SW-03 | P0 | 师傅判断录入：阶段、香气、柔软度、红边、失水感受、下一步建议、置信度与备注 | `MASTER_CHECK` 事件入口、标签表单和 `master_labels.csv` | 标签关联批次、事件、记录人和时间；字段有枚举/范围校验；量表定义有版本；允许明确记录“未判断”，不默认填入中间分数；修改保留修订记录 |
| SW-04 | P1 | 批次信息与设备档案：品种、产地、采摘条件、初始质量、实验方案、设备身份、固件/软件版本和标定参数 | `SessionLogger.start`、批次表单和设备信息接收 | 每批元数据可独立解释；未知信息明确留空；区分电脑模拟、串口mock与实测；记录实际设备版本和软件SHA/工作区修改状态；批次中配置变化有记录 |
| SW-05 | P0 | 采集可靠性：后台写盘、持久化故障日志、掉线恢复、写入队列和退出收尾 | `SensorReader`、`on_sensor`、独立写入工作线程与健康监测 | 在接收线程打时间戳；有限队列满时明确报错，不静默丢弃；接收、写入与丢弃计数可核对；掉线/复位/重连有记录；退出前处理待写数据，失败时保留未完成标记 |
| SW-06 | P2 | 历史批次回放与对比：曲线、图像、事件、标签同步查看，多批次对照 | 新增批次读取/回放模块；复用现有图表与检查模块 | 可打开旧格式及新格式批次；不修改原始目录；缺图/缺列/异常时间轴给出提示；支持按批次相对时间或工艺事件对齐；模拟与实测来源可见 |
| SW-07 | P2 | 实验分析与报告：缺包、基线漂移、重复性、失水曲线、图表和报告导出 | 扩展 `session_check.py`，另设分析模块与版本化输出目录 | 指标可追溯到原始行及处理参数；重启序号与真正缺包区分；明确基线/稳定窗口和排除规则；不把未定义或无效指标填成0；导出可复算且不覆盖原始数据 |

### 10.2 建议实施顺序与依赖

下一轮以 **设备操作面板＋后台写盘＋自动拍照＋师傅标签录入** 为交付范围；批次元数据的必要字段随流程补齐，完整档案管理后续扩展。

1. **先建立接收、命令与存储边界**：串口仅由一个工作线程持有；界面通过信号/队列请求发送，收到状态响应后更新界面。后台写盘与接收解耦，先定义正常结束和异常结束流程。
2. **接入设备面板**：为每次操作记录请求、设备响应和最终结果。当前固件响应没有请求ID，初版应限制同时只有一个待完成操作，且区分“已接受命令”和“操作已完成”；如需并发，先扩展协议与响应关联测试。
3. **加入相机与事件关联**：相机线程返回实际采图时间、保存结果和文件名，由批次记录模块统一落索引。事件触发拍照和定时拍照共用调度，避免重复并发操作相机。
4. **加入标签表单**：与现有 `MASTER_CHECK` 事件绑定；先确定量表定义与未知值表示，再采集正式标签。标签录入失败时不丢失已经保存的事件。
5. **完成元数据管理后再做回放和分析**：统一时间、单位、批次来源、标定与文件关系；历史回放作为检查分析输入是否正确的入口。

现有固件驱动代码已实现，硬件侧下一步是按 [固件验证记录](../../hardware/esp32_s3_mvp/VALIDATION.md) 逐路实测，不再把“从mock替换驱动”列为尚未编写的软件任务。

### 10.3 数据与设备操作约束

- 设备面板必须显示“命令状态”和“真实反馈”的区别；目前泵阀只有命令输出，没有流量/阀位传感器，不显示未经测量的“阀已到位”或“流量正常”。
- 断线重连先读取设备身份与状态；标定、开泵、开阀命令不自动重试或恢复。采集中是否允许重新标定须有明确状态规则，不能静默改变同一批次的质量基准。
- 原始传感器帧、设备健康日志、命令结果、图片索引和人工标签分别存储，统一使用批次ID、带时区时间及主机单调时钟关联；传感器帧继续保留MCU时间。
- `image_index.csv` 和 `master_labels.csv` 沿用前期数据格式设计，并补充关联ID及版本；新增字段时同时更新写入、读取、完整性检查和兼容测试。
- 相机断开、写盘失败、队列积压、设备复位都要能定位到时间段。后台写盘改善响应性，不等价于断电零丢失；必须明确缓存与持久化边界。
- 分析文件写入版本化处理/报告目录，记录来源批次、算法版本和参数。重复性指标需要可比的重复实验，状态识别与工艺建议需要真实数据及独立验证，不能由模拟曲线推导性能结论。

### 10.4 模拟验证与实物验收边界

SW-01至SW-05的大部分界面、状态机和文件流程可先用模拟设备完成。模拟测试需包含：命令被拒绝/超时、串口断开与设备复位、相机失败、慢磁盘、写入错误、队列积压、结束批次与关闭窗口，以及连续创建多个批次。

模拟通过后仍须接板验证真实响应、泵阀互锁、标定持久化、图像采集、测量精度及至少8小时连续运行。每项开发完成时记录代码版本、测试范围与未验证部分，再将路线表中的对应项更新为已完成。

状态识别、工艺推荐和自适应控制安排在多批次真实数据及品质反馈具备之后；当前只预留接口，不写死“最佳状态”或对外宣称模型效果。

## 11. 修改与交付约定

新增字段时同步修改固件、`SENSOR_FIELDS`/映射、检查规则、测试与本文。改变字段含义、采样率或故障语义时升级协议/软件版本，不静默解释旧数据。算法特征另存处理目录，不覆盖原始批次。提交前运行相关测试和 `git diff --check`，不提交 `.venv`、缓存或真实采集数据。

## 12. 系统工程补充与执行层开发路线

本节用于约束从“采集平台”向“可执行、可追溯、可安全运行的做青原型系统”演进。当前目标不是堆功能，而是先建立一套即使暂时没有状态识别算法，也能稳定完成整批做青实验并复现全过程的系统。

### 12.1 六层系统边界

后续开发统一按六层组织，避免把算法、控制、硬件和原始数据混在一起：

```text
① 感知层
VOC / RGB / 温湿度 / 叶温 / 称重 / RPM / 电机状态

② 执行层
气泵 / 采样阀 / 清洗阀 / 摇青滚筒 / 风机 / 环境调节

③ 控制层
ESP32-S3 / 安全互锁 / 设备驱动 / 转速闭环

④ 数据层
原始串口 / 传感器表 / 事件 / 图片 / 标签 / 标定 / 版本信息

⑤ 分析层
回放 / 特征提取 / 漂移分析 / 批次比较 / 状态估计

⑥ 决策层
工艺建议 / 人工确认 / 半自动 / 闭环控制
```

当前开发重点保持在①～④层；⑤～⑥层只预留接口，不因模拟数据提前训练或宣称模型性能。

### 12.2 摇青滚筒与电机执行子系统

摇青执行机构可以与感知系统并行设计，但必须将“执行机构可控”和“算法自动决定工艺”分开。

第一阶段目标：

- 小型摇青滚筒或可调速实验平台；
- 电机启停；
- 目标转速设定；
- 实际转速反馈；
- 运行方向；
- 运行时长；
- 电机故障状态；
- 必要时记录电机电流或驱动器负载信息；
- 上位机人工控制，不由状态模型自动触发。

推荐控制链：

```text
上位机
  ↓ 工艺命令
ESP32-S3
  ↓
电机驱动器 / 变频器
  ↓
减速电机
  ↓
摇青滚筒
  ↑
编码器 / 霍尔转速反馈
```

建议新增并长期保留以下过程字段：

```text
shake_target_rpm
shake_actual_rpm
shake_direction
shake_start_time
shake_end_time
shake_duration_s
motor_current_a        # 有可靠采集条件时
motor_fault
```

首批真实做青仍由人工决定“何时摇、摇多久、摇多快”，系统只负责可靠执行与完整记录。多批次数据、师傅标签和品质反馈具备后，才进入“系统建议 → 人工确认 → 自动执行”，最终再考虑闭环自适应控制。

### 12.3 环境调节执行器的边界

环境温湿度必须连续监测，但加热、加湿、除湿和制冷不作为第一版必装执行器。先采集真实做青环境与失水数据，再决定需要哪一种调节能力。

优先级建议：

| 执行项 | 当前策略 |
|---|---|
| 环境循环风机 | 中高优先级，可较早加入 |
| 加热 | 预留控制接口，根据真实环境决定是否安装 |
| 加湿 | 预留控制接口，根据失水与环境数据决定是否安装 |
| 除湿 | 预留控制接口，高湿环境下可能比加湿更重要 |
| 制冷 | 后续按现场环境决定 |
| 直接向鲜叶喷雾 | 不采用默认方案 |
| 裸加热棒直接辐射鲜叶 | 不采用默认方案 |

环境调节应作用于空气或风道，不直接向鲜叶喷雾或局部加热，避免污染称重失水、视觉和VOC数据。正式加入环境执行器时，必须同时记录目标值、实际值、执行状态和故障状态。

### 12.4 电源、安全与硬件互锁

滚筒、电机、气泵、阀门和后续环境执行器加入后，必须把安全作为独立设计项，不依赖上位机正常运行。

最低要求：

- 3.3 V / 5 V / 12 V 等电源分域清楚；
- 模拟采集、数字控制与电机/气泵等噪声负载尽量隔离；
- 保险、反接、过流和必要的浪涌/续流保护；
- 所有执行输出上电默认关闭；
- 滚筒具备独立硬件急停；
- 机械结构具备必要的防夹、防卷入措施；
- 条件允许时加入门盖/防护罩状态检测；
- 设备断线、MCU复位、上位机崩溃时不得自动恢复危险动作；
- 气路和滚筒的硬件使能与软件命令分离。

安全链的原则是：急停和关键互锁能够在不依赖PC软件的情况下切断执行机构。

### 12.5 原始数据与数字追溯

在正式实验前增加原始串口留档能力，建议每批新增：

```text
raw_serial.jsonl
```

ESP32发送的原始JSON行应在解析前保存，使后续即使发现解析程序缺陷，也能从原始数据重新生成结构化表。被拒绝帧、解析失败和设备状态消息也应保留在可追溯日志中，不能只显示在GUI后丢失。

每批实验的 `meta.yaml` 最终至少应记录：

```text
batch_id
host_software_version
host_git_commit
host_worktree_dirty
firmware_version
hardware_version
device_id
sensor_model_and_batch
calibration_version
experiment_protocol_version
operator
source_mode
```

Git SHA、固件版本、硬件版本、传感器批次、标定记录和SOP版本共同构成批次“数字身份证”。未知值明确留空，不使用看似完整的占位值冒充实测信息。

### 12.6 校准、自检与开机验收

正式实验前建立分设备校准与自检流程：

- ADC：已知安全电压与万用表交叉验证；
- HX711：去皮、标准砝码、多点误差和重复性；
- SHT31：与参考温湿度计比较；
- MLX90614：固定距离条件下与参考温度比较；
- RGB相机：固定机位、固定曝光、固定白平衡、固定光照和背景，条件允许时使用色卡；
- MOS：记录预热、洁净空气基线、重复性和恢复过程；
- 转速反馈：与独立转速计或可追溯方法比较；
- 电机电流：若作为记录变量，须明确传感器量程和零点误差。

开机自检至少检查：设备身份、I²C设备、启用通道、称重标定状态、摄像头、磁盘空间、串口数据连续性和执行器默认关闭状态。自检通过只代表系统可开始实验，不代表传感器精度已经验证。

### 12.7 故障注入与恢复测试

正式做青前除正常流程外，必须主动测试异常场景：

- 拔出USB/串口；
- ESP32复位；
- 单个I²C传感器断开；
- 相机掉线或被占用；
- 慢磁盘、磁盘不足、写入失败；
- 写入队列积压；
- 执行器命令被拒绝或超时；
- 气路使能断开；
- 滚筒运行中急停；
- 程序关闭和电脑异常退出。

每种故障都要能回答三个问题：是否安全、是否留下时间点和原因、恢复后是否会误续写或自动重放危险命令。

### 12.8 当前推荐开发顺序

在真实算法开发前，优先按以下顺序收敛工程底座：

1. SW-05：采集可靠性、后台写盘、故障日志、退出收尾；
2. SW-02：自动拍照、图片索引与事件关联；
3. SW-03：师傅结构化标签；
4. SW-01：设备操作面板；
5. SW-04：批次元数据与版本追溯；
6. 原始 `raw_serial.jsonl` 与被拒绝帧留档；
7. 滚筒、电机、调速和转速反馈的人工控制原型；
8. 真实板卡、传感器、气路与执行机构逐项验收；
9. 4～8小时连续运行和故障注入测试；
10. 第一批真实做青被动监测与人工控制实验；
11. 有多批次真实数据后再开发状态估计、工艺推荐和自适应控制。

### 12.9 本阶段停止扩张条件

当系统满足以下条件后，应暂停继续堆软件功能，把主要精力转向真实实验：

- 即使没有任何状态识别算法，也能稳定完成一整批做青数据采集；
- 所有传感、图片、师傅标签、工艺事件和执行参数能统一时间关联；
- 任一批次可追溯到软件、固件、硬件、标定和实验协议版本；
- 串口、相机、磁盘和设备故障可定位，不静默丢数据；
- 执行机构发生异常时系统进入安全状态；
- 原始数据可用于重新解析，处理结果不会覆盖原始记录；
- 完成至少一次长时间运行和异常恢复验收。

达到这一节点后，新增“更复杂UI、更多模型、更自动的决策”都应由真实实验需求驱动，而不是为了增加功能数量。
