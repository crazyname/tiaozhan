## 3. 环境与运行

Windows，依赖范围见 `requirements.txt`；本机验证使用已有Python环境，具体版本见验证记录。摄像头使用DirectShow、编号0，请求1920×1080；实际分辨率取决于设备。

```powershell
cd D:\tiaozhan\software\host_mvp
.\.venv\Scripts\python.exe app.py --simulate
.\.venv\Scripts\python.exe app.py --port COM7 --baud 115200
.\.venv\Scripts\python.exe -m unittest discover -p "test_*.py" -v
```

默认端口COM5，默认115200波特。尚未创建环境时按README安装依赖。模拟模式同时生成模拟传感器和带水印的模拟图片，不用于实验结论。

## 4. 数据流与线程边界

```text
串口/模拟 → SensorReader：接收时间、原始字节入队、解析、字段映射
                  ├→ 有限写盘队列 → BatchWriter → CSV / JSONL / YAML
                  └→ Qt信号 → 界面显示（不负责传感器落盘）
人工事件/标签 → 同一批次写盘队列
定时/事件拍照 → CameraWorker → 图片文件 → 图片索引入队 → 界面预览
停止批次 → 停止接收批次数据 → 等待已提交照片 → 排空写盘队列 → 检查报告
```

批次写盘队列默认2048条，相机队列8项，连接日志队列4096条。队列满会报错；批次写盘拒收后停止该批次并排空已接收记录。每条写入后flush，但没有逐条fsync，不能保证断电零丢失。检查报告在后台生成。批次初始化及Git版本读取仍在开始操作内同步执行。

## 5. 协议与命令

沿用固件JSONL-v0.2和旧版传感器字段。`seq`必须为非负整数，`gas_adc`、`gas_v`为数组；不足4路补空。设备质量标记原样保留，跳号追加`SERIAL_GAP`；默认通道掩码15，硬件三路配置为7，未启用通道不要求数值。完整解析帧保存在`device_frame_json`，原始字节另存。

串口由一个线程读写。自动连接只发送`info`；人工操作支持`info/tare/calibrate/air/stop`，采样/吹扫时长1～120秒，标定质量0～20000g（不含0）。去皮和标定在批次外进行。

固件没有请求ID，主机只允许一个待完成命令；本地`request_id`仅用于日志，不是设备关联保证。标定收到“collecting”保持执行中，收到保存/拒绝状态才结束；气路accepted仅表示命令被接受，不是阀位反馈或运行完成。动作超时标为结果未知，不重试；断线清空待发队列，重连后需要人工确认并重新连接才能继续动作。只读信息查询超时允许旧设备继续被动采集。

**结束批次、断开串口或关闭窗口并不保证立即关闭物理气路。操作人员应先点击“停止气路”并检查设备；气路命令自身有限时保护，软件按钮不替代硬件使能和急停。** 当前停止命令只停止气路，不取消正在执行的称重标定。

## 6. 批次文件与追溯

```text
data/raw/<batch_id>/
  meta.yaml                软件SHA、工作区状态、来源、设备配置及批次信息
  sensor_1hz.csv           原有传感器列、质量标记、完整解析帧
  events.csv              人工/系统事件
  raw_serial.jsonl         解析前原始字节（Base64）、文本及接收时间
  device_health.jsonl      状态、异常和设备配置变化
  commands.jsonl           排队、发送、响应、超时等命令阶段
  image_index.csv         图片相对路径、批次、时间、事件、来源、曝光/白平衡读数
  master_labels.csv       版本化人工标签及追加修订链
  images/*.jpg
  writer_summary.json     accepted/written/rejected/unwritten和错误
  session_check.txt        收尾检查结果
  INCOMPLETE              运行中存在；成功收尾移除，失败保留
```

连接期间另存`data/device_logs/*.jsonl`，覆盖批次前的标定及批次外错误。上述运行数据不加入Git，需另行备份。原始JSONL存储Base64，因此无效UTF-8、解析失败行和断开时残留片段也可还原；接收时间表示主机读到完整行/片段的时间，不是设备采样的精密同步时间。

批次名限制为1～80个字母、数字、下划线或短横线，不允许路径及系统保留名，也不覆盖已有目录。结束期间禁止新批次，等待图片完成后写SESSION_END并关闭文件。旧批次照片回调带独立令牌，不能写到新批次。

元数据记录host版本、Git SHA及dirty状态、设备上报版本/身份/标定参数；“批次 / 标定 / SOP 档案”可录入品种、产地、方案编号、采摘条件、传感器型号批次、标定版本/日期/参考仪表/记录及SOP版本/文档内容或位置，未知明确为空。没有来源字段的旧串口源标为`serial_unverified`，不能当作已确认实测；设备上报来源也不等于外部真实性认证。初始装料质量可人工指定；留空才采用第一条正且有限的称重，均记录来源，仍需人工核对。

## 7. 图片与标签

自动拍照默认开启：批次开始、每30秒及关键事件补拍；取消自动拍照后仍可手动拍照。成功写入照片后才提交索引，失败记录健康日志。图片时间为读取完成时间，关联事件表示触发来源，不保证严格同步曝光。v0.7可请求固定曝光/白平衡并保存驱动读回，见第17节；色卡校正和画质判断仍未实现。

师傅检查先记录MASTER_CHECK事件，再打开表单；取消表单保留事件。所有评分默认未判断，CSV空值代表未知。量表是1～5级有序草案，详见LABEL_SCALE.md，尚未验证观察者一致性。修订最近标签会追加新行，增加revision并通过supersedes指向前一条，不覆盖历史。

## 8. 检查与验收

保留序号/时间/缺值/质量标记/范围/通道掩码/事件起止和磁盘空间检查；新增INCOMPLETE、写盘汇总、图片文件与索引一致性、标签事件和修订链检查。旧批次无新表时兼容读取。报告不验证图像内容、标签科学有效性或所有器件专用量程。

测试使用临时目录、模拟源和替身串口；不自动操作真实泵阀。具体测试结果及未覆盖项见VALIDATION.md。正式实验仍需ESP32-S3-DevKitC-1 N8R8、真实传感器、摄像头及至少8小时联机验收。

## 9. 已知限制与后续入口

- 原生摄像头驱动在独立子进程运行，超时/关闭可终止；已验证注入卡死恢复，真实相机拔插仍待验收。
- 连接日志写入错误会在界面提示并停止当前批次；故障未修复时禁止新批次，恢复需重启程序。日志按16MiB轮转，单会话64段后停止并报错，保留历史文件，不自动删除实验记录。
- 串口重连间隔2秒，恢复只读采集，不恢复动作；序号倒退记录设备复位或乱序，尚未区分所有原因。
- 写盘汇总用于核对主机已接收记录；队列满或磁盘故障后的数据不保证完整，保留INCOMPLETE及错误说明。
- 没有真实设备验收、8小时稳定性结果、算法报告或滚筒驱动实现；历史回放和批次对比见第15节。

### 10.2 建议实施顺序与依赖

下一轮以 **设备操作面板＋后台写盘＋自动拍照＋师傅标签录入** 为交付范围；批次元数据的必要字段随流程补齐，完整档案管理后续扩展。

1. **先建立接收、命令与存储边界**：串口仅由一个工作线程持有；界面通过信号/队列请求发送，收到状态响应后更新界面。后台写盘与接收解耦，先定义正常结束和异常结束流程。
2. **接入设备面板**：为每次操作记录请求、设备响应和最终结果。当前固件响应没有请求ID，初版应限制同时只有一个待完成操作，且区分“已接受命令”和“操作已完成”；如需并发，先扩展协议与响应关联测试。
3. **加入相机与事件关联**：相机线程返回实际采图时间、保存结果和文件名，由批次记录模块统一落索引。事件触发拍照和定时拍照共用调度，避免重复并发操作相机。
4. **加入标签表单**：与现有 `MASTER_CHECK` 事件绑定；先确定量表定义与未知值表示，再采集正式标签。标签录入失败时不丢失已经保存的事件。
5. **完成元数据管理后再做回放和分析**：统一时间、单位、批次来源、标定与文件关系；历史回放作为检查分析输入是否正确的入口。

现有固件驱动代码已实现，硬件侧下一步是按 [固件验证记录](../../hardware/esp32_s3_mvp/VALIDATION.md) 逐路实测，不再把“从mock替换驱动”列为尚未编写的软件任务。

### 10.3 数据与设备操作约束

- 设备面板必须显示“命令状态”和“真实反馈”的区别；目前泵阀只有命令输出，没有流量/阀位传感器，不显示未经测量的“阀已到位”或“流量正常”。
- 断线重连先读取设备身份与状态；标定、开泵、开阀命令不自动重试或恢复。采集中是否允许重新标定须有明确状态规则，不能静默改变同一批次的质量基准。
- 原始传感器帧、设备健康日志、命令结果、图片索引和人工标签分别存储，统一使用批次ID、带时区时间及主机单调时钟关联；传感器帧继续保留MCU时间。
- `image_index.csv` 和 `master_labels.csv` 沿用前期数据格式设计，并补充关联ID及版本；新增字段时同时更新写入、读取、完整性检查和兼容测试。
- 相机断开、写盘失败、队列积压、设备复位都要能定位到时间段。后台写盘改善响应性，不等价于断电零丢失；必须明确缓存与持久化边界。
- 分析文件写入版本化处理/报告目录，记录来源批次、算法版本和参数。重复性指标需要可比的重复实验，状态识别与工艺建议需要真实数据及独立验证，不能由模拟曲线推导性能结论。

### 10.4 模拟验证与实物验收边界

SW-01至SW-05的大部分界面、状态机和文件流程可先用模拟设备完成。模拟测试需包含：命令被拒绝/超时、串口断开与设备复位、相机失败、慢磁盘、写入错误、队列积压、结束批次与关闭窗口，以及连续创建多个批次。

模拟通过后仍须接板验证真实响应、泵阀互锁、标定持久化、图像采集、测量精度及至少8小时连续运行。每项开发完成时记录代码版本、测试范围与未验证部分，再将路线表中的对应项更新为已完成。

状态识别、工艺推荐和自适应控制安排在多批次真实数据及品质反馈具备之后；当前只预留接口，不写死“最佳状态”或对外宣称模型效果。

## 11. 修改与交付约定

新增字段时同步修改固件、`SENSOR_FIELDS`/映射、检查规则、测试与本文。改变字段含义、采样率或故障语义时升级协议/软件版本，不静默解释旧数据。算法特征另存处理目录，不覆盖原始批次。提交前运行相关测试和 `git diff --check`，不提交 `.venv`、缓存或真实采集数据。

## 12. 系统工程补充与执行层开发路线

本节用于约束从“采集平台”向“可执行、可追溯、可安全运行的做青原型系统”演进。当前目标不是堆功能，而是先建立一套即使暂时没有状态识别算法，也能稳定完成整批做青实验并复现全过程的系统。

### 12.1 六层系统边界

后续开发统一按六层组织，避免把算法、控制、硬件和原始数据混在一起：

```text
① 感知层
VOC / RGB / 温湿度 / 叶温 / 称重 / RPM / 电机状态

② 执行层
气泵 / 采样阀 / 清洗阀 / 摇青滚筒 / 风机 / 环境调节

③ 控制层
ESP32-S3 / 安全互锁 / 设备驱动 / 转速闭环

④ 数据层
原始串口 / 传感器表 / 事件 / 图片 / 标签 / 标定 / 版本信息

⑤ 分析层
回放 / 特征提取 / 漂移分析 / 批次比较 / 状态估计

⑥ 决策层
工艺建议 / 人工确认 / 半自动 / 闭环控制
```

当前开发重点保持在①～④层；⑤～⑥层只预留接口，不因模拟数据提前训练或宣称模型性能。

### 12.2 摇青滚筒与电机执行子系统

摇青执行机构可以与感知系统并行设计，但必须将“执行机构可控”和“算法自动决定工艺”分开。

第一阶段目标：

- 小型摇青滚筒或可调速实验平台；
- 电机启停；
- 目标转速设定；
- 实际转速反馈；
- 运行方向；
- 运行时长；
- 电机故障状态；
- 必要时记录电机电流或驱动器负载信息；
- 上位机人工控制，不由状态模型自动触发。

推荐控制链：

```text
上位机
  ↓ 工艺命令
ESP32-S3
  ↓
电机驱动器 / 变频器
  ↓
减速电机
  ↓
摇青滚筒
  ↑
编码器 / 霍尔转速反馈
```

建议新增并长期保留以下过程字段：

```text
shake_target_rpm
shake_actual_rpm
shake_direction
shake_start_time
shake_end_time
shake_duration_s
motor_current_a        # 有可靠采集条件时
motor_fault
```

首批真实做青仍由人工决定“何时摇、摇多久、摇多快”，系统只负责可靠执行与完整记录。多批次数据、师傅标签和品质反馈具备后，才进入“系统建议 → 人工确认 → 自动执行”，最终再考虑闭环自适应控制。

### 12.3 环境调节执行器的边界

环境温湿度必须连续监测，但加热、加湿、除湿和制冷不作为第一版必装执行器。先采集真实做青环境与失水数据，再决定需要哪一种调节能力。

优先级建议：

| 执行项 | 当前策略 |
|---|---|
| 环境循环风机 | 中高优先级，可较早加入 |
| 加热 | 预留控制接口，根据真实环境决定是否安装 |
| 加湿 | 预留控制接口，根据失水与环境数据决定是否安装 |
| 除湿 | 预留控制接口，高湿环境下可能比加湿更重要 |
| 制冷 | 后续按现场环境决定 |
| 直接向鲜叶喷雾 | 不采用默认方案 |
| 裸加热棒直接辐射鲜叶 | 不采用默认方案 |

环境调节应作用于空气或风道，不直接向鲜叶喷雾或局部加热，避免污染称重失水、视觉和VOC数据。正式加入环境执行器时，必须同时记录目标值、实际值、执行状态和故障状态。

### 12.4 电源、安全与硬件互锁

滚筒、电机、气泵、阀门和后续环境执行器加入后，必须把安全作为独立设计项，不依赖上位机正常运行。

最低要求：

- 3.3 V / 5 V / 12 V 等电源分域清楚；
- 模拟采集、数字控制与电机/气泵等噪声负载尽量隔离；
- 保险、反接、过流和必要的浪涌/续流保护；
- 所有执行输出上电默认关闭；
- 滚筒具备独立硬件急停；
- 机械结构具备必要的防夹、防卷入措施；
- 条件允许时加入门盖/防护罩状态检测；
- 设备断线、MCU复位、上位机崩溃时不得自动恢复危险动作；
- 气路和滚筒的硬件使能与软件命令分离。

安全链的原则是：急停和关键互锁能够在不依赖PC软件的情况下切断执行机构。

### 12.5 原始数据与数字追溯

在正式实验前增加原始串口留档能力，建议每批新增：

```text
raw_serial.jsonl
```

ESP32发送的原始JSON行应在解析前保存，使后续即使发现解析程序缺陷，也能从原始数据重新生成结构化表。被拒绝帧、解析失败和设备状态消息也应保留在可追溯日志中，不能只显示在GUI后丢失。

每批实验的 `meta.yaml` 最终至少应记录：

```text
batch_id
host_software_version
host_git_commit
host_worktree_dirty
firmware_version
hardware_version
device_id
sensor_model_and_batch
calibration_version
experiment_protocol_version
operator
source_mode
```

Git SHA、固件版本、硬件版本、传感器批次、标定记录和SOP版本共同构成批次“数字身份证”。未知值明确留空，不使用看似完整的占位值冒充实测信息。

### 12.6 校准、自检与开机验收

正式实验前建立分设备校准与自检流程：

- ADC：已知安全电压与万用表交叉验证；
- HX711：去皮、标准砝码、多点误差和重复性；
- SHT31：与参考温湿度计比较；
- MLX90614：固定距离条件下与参考温度比较；
- RGB相机：固定机位、固定曝光、固定白平衡、固定光照和背景，条件允许时使用色卡；
- MOS：记录预热、洁净空气基线、重复性和恢复过程；
- 转速反馈：与独立转速计或可追溯方法比较；
- 电机电流：若作为记录变量，须明确传感器量程和零点误差。

开机自检至少检查：设备身份、I²C设备、启用通道、称重标定状态、摄像头、磁盘空间、串口数据连续性和执行器默认关闭状态。自检通过只代表系统可开始实验，不代表传感器精度已经验证。

### 12.7 故障注入与恢复测试

正式做青前除正常流程外，必须主动测试异常场景：

- 拔出USB/串口；
- ESP32复位；
- 单个I²C传感器断开；
- 相机掉线或被占用；
- 慢磁盘、磁盘不足、写入失败；
- 写入队列积压；
- 执行器命令被拒绝或超时；
- 气路使能断开；
- 滚筒运行中急停；
- 程序关闭和电脑异常退出。

每种故障都要能回答三个问题：是否安全、是否留下时间点和原因、恢复后是否会误续写或自动重放危险命令。

### 12.8 当前推荐开发顺序

在真实算法开发前，优先按以下顺序收敛工程底座：

1. SW-05：采集可靠性、后台写盘、故障日志、退出收尾；
2. SW-02：自动拍照、图片索引与事件关联；
3. SW-03：师傅结构化标签；
4. SW-01：设备操作面板；
5. SW-04：批次元数据与版本追溯；
6. 原始 `raw_serial.jsonl` 与被拒绝帧留档；
7. 滚筒、电机、调速和转速反馈的人工控制原型；
8. 真实板卡、传感器、气路与执行机构逐项验收；
9. 4～8小时连续运行和故障注入测试；
10. 第一批真实做青被动监测与人工控制实验；
11. 有多批次真实数据后再开发状态估计、工艺推荐和自适应控制。

### 12.9 本阶段停止扩张条件

当系统满足以下条件后，应暂停继续堆软件功能，把主要精力转向真实实验：

- 即使没有任何状态识别算法，也能稳定完成一整批做青数据采集；
- 所有传感、图片、师傅标签、工艺事件和执行参数能统一时间关联；
- 任一批次可追溯到软件、固件、硬件、标定和实验协议版本；
- 串口、相机、磁盘和设备故障可定位，不静默丢数据；
- 执行机构发生异常时系统进入安全状态；
- 原始数据可用于重新解析，处理结果不会覆盖原始记录；
- 完成至少一次长时间运行和异常恢复验收。

达到这一节点后，新增“更复杂UI、更多模型、更自动的决策”都应由真实实验需求驱动，而不是为了增加功能数量。

## 14. v0.4 阶段：SW-04 批次档案

- `metadata.py` 定义 `batch-metadata-v1`：人工字段白名单、未知空值、质量正数校验、档案 JSON 导入/另存新版本及 SHA256 一致性检查。禁止人工档案覆盖软件/设备身份和来源。
- GUI 支持完整档案编辑，活动批次及收尾期间锁定；载入档案或结束批次清空装料质量，防止错误复用。
- 每批元数据包含独立 `operator_metadata` 快照、校验摘要、初始质量及来源、初始设备配置与最新配置。配置改变写入带时间日志，不改变人工快照。
- `session_check.py` 检查新版快照校验，旧批次不要求新增字段。档案校验仅用于识别意外修改，不是真实性认证。
- 标定/SOP 文档位置属于引用，外部文件不会自动复制；需在备注保存足够的方法与结果，并自行归档引用文件。此功能不自动执行传感器精度验收。
- SW-04 软件管理阶段完成；SW-06、SW-07、相机阻塞恢复、日志轮转及执行层继续开发；所有实物验收仍待进行。

## 15. v0.5 阶段：SW-06 历史回放与对比

- `replay.py` 只读加载新/旧批次，保留 CSV 记录序号、原字段、来源和异常提示；`replay_ui.py` 在后台读入快照，提供多批次叠加、事件次数对齐、游标、倍速、照片/事件/标签联动。
- 时间基准统一采用主机单调时间；传感器表完全没有可用单调时间时才对所有表采用带时区 ISO 日期。无可用时间的记录不参与回放并计数提示；不制造时间、不修复原始文件。时间倒退明确告警后只对显示排序。
- 按批次起点或第 N 次事件对齐，缺事件批次明确排除；来源显示在图例。失水采用元数据初始质量，旧批次没有时取首个有效正质量并提示。
- 照片路径必须位于批次 images 内；缺图/解码失败提示。标签显示截至游标的最近记录（含追加修订），历史 CSV 不改写。
- 文件哈希前后相等测试验证读取不修改原数据。GUI 测试覆盖两批对齐、标签游标、事件跳转与播放状态；offscreen 渲染检查布局。
- 这是查看与对比工具，不含自动科研结论；SW-07 分析与报告继续开发。硬件及长期验收状态不变。

## 16. v0.6 阶段：SW-07 工程分析与可复算报告

- `analysis.py` 定义 `engineering-analysis-v1`，使用回放只读快照；GUI后台导出及CLI都使用同一参数和计算实现。
- 用户定义不重叠基线/稳定半开区间。质量标记、非有限值、禁用通道、重复时间和无效时间分别记录排除原因/记录序号；不修改原始行。输出均值、样本标准差、OLS斜率、稳定减基线均值以及质量/失水曲线，未定义为null。
- 原CSV顺序检查序号和MCU时钟：时钟倒退建立新段，倒序/重复单列；段内使用已见序号集合推测缺号，允许迟到帧填补。不能仅凭序号区分所有复位、乱序及设备未发送原因，报告明确保留推测语义。
- 重复性需人工提供同组ID，档案关键字段完整且一致，来源一致且可解释，稳定窗口完整覆盖且每批有至少两点；不同条件拒绝汇总，不将模拟计算当作真实重复性结论。
- 独立输出目录包含版本/时间/随机ID，拒绝写入原批次；输入文件哈希在读入前后及导出结束核对，输入变化或未完成批次拒绝完成报告。输出含HTML、JSON、CSV和Matplotlib图表；参数、版本、文件SHA256及原CSV记录序号供复算。
- GUI读取/分析在工作线程完成，关闭时等待任务结束；原始批次完整性检查仍由 `session_check.py` 负责。报告不判断基线是否真正洁净、不校准传感器、不训练状态模型。
- 软件阶段SW-01～SW-07已具备相应功能；相机阻塞恢复、日志轮转、执行层及实物/长期验收仍待推进，不能据此宣称系统已完成实验验证。

## 17. v0.7 阶段：相机恢复与日志容量

- `camera_process.py` 在spawn子进程内独占真实DirectShow设备，打开/设置/采图/编码均处于8秒请求期限内；父线程超时或关闭时结束子进程并完成失败回调。子进程不接触批次文件，只有父线程收到成功JPEG后写盘。
- 下次请求重建失败进程；关闭时取消排队照片并记录CAMERA_ERROR；正常结束批次仍等待照片完成或超时。注入测试覆盖卡死、重建、关闭及待保存计数归零，不证明所有真实驱动或系统级I/O故障均已验收。
- 相机编号、固定曝光/白平衡请求写入meta；图片note记录请求和驱动读回。DirectShow自动曝光/白平衡设置0表示手动，依据[OpenCV后端实现](https://github.com/opencv/opencv/blob/4.x/modules/videoio/src/cap_dshow.cpp)。不支持的自动状态getter记录None；setter成功与读回吻合也不等价于光学标定或真实画面稳定，仍需固定光照/色卡验收。
- `DiagnosticJournal` 按UTF-8字节数切分完整JSONL记录，默认16MiB一段、64段上限；新段使用独占创建，历史数据不覆盖、不删除，超限进入既有日志故障路径。单条超限也报告失败，禁止静默截断原始记录。
- 原始批次日志不受连接日志轮转影响。归档/保留期限由实验负责人决定；真实相机、设备和8小时联机验收仍未执行。
